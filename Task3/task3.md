# Задание 3. Оценка Data Encryption at Rest and In Transit

Необходимо разработать стратегию защиты данных в рамках всей системы. При этом важно учесть особенности шифрования данных, которые находятся в разных состояниях — при хранении и во время передачи. 

Стратегия строится на эшелонированной защите:
1.  **Шифрование при передаче (In Transit):** Весь трафик, выходящий за пределы сервиса, должен быть зашифрован.
2.  **Шифрование при хранении (At Rest):** Данные на дисках и в базах данных зашифрованы, ключи хранятся отдельно от данных.
3.  **Управление ключами:** Централизованное хранилище секретов (Vault), чтобы ключи не лежали в коде или конфигах.

| Данные | В чём необходимость защиты | Инструменты защиты |
| :--- | :--- | :--- |
| **1. Персональные данные (PII) пациентов и сотрудников**<br>*(ФИО, паспортные данные, адрес, телефон, email, СНИЛС)* | **Юридическая:** Соблюдение 152-ФЗ.<br>**Репутационная:** Потеря доверия при утечке базы клиентов.<br>**Риск:** Кража личной информации, спам, мошенничество. | **In Transit:** TLS 1.3 (HTTPS)<br>**At Rest (БД):** Шифрование дисков. Шифрование на уровне колонок БД (pgcrypto в Postgres).<br>**Доступ:** Маскирование данных при отображении. |
| **2. Медицинские данные (PHI)**<br>*(Диагнозы, результаты анализов, заключения врачей, история болезни, файлы сканов/PDF)* | **Юридическая:** Врачебная тайна (323-ФЗ). Особая категория ПДн.<br>**Этическая:** Информация приватного характера.<br>**Риск:** Шантаж пациентов, дискриминация, моральный ущерб. | **At Rest (Файлы):** Server-Side Encryption (SSE) в MinIO (S3) с использованием ключей из Vault.<br>**At Rest (БД):** Application-Level Encryption (шифрование на уровне Java-приложения перед записью в БД), чтобы даже администратор БД не видел диагнозы.<br>**Доступ:** RBAC (Врач видит только своих пациентов). |
| **3. Аутентификационные данные и секреты**<br>*(Пароли пользователей, API-ключи, приватные ключи сертификатов, ключи шифрования БД)* | **Критическая:** Утечка этих данных компрометирует всю систему защиты.<br>**Риск:** Полный захват инфраструктуры злоумышленниками. | **Storage:** HashiCorp Vault (для хранения секретов и ротации ключей).<br>**DevOps:** Запрет на хранение секретов в Git. Использование Sealed Secrets в Kubernetes.<br>**Аутентификация:** Хеширование паролей (Argon2 / bcrypt) в Keycloak. |
| **4. Финансовые данные**<br>*(Транзакции, данные чеков, зарплатные ведомости, данные для налоговой)* | **Финансовая:** Риск мошенничества, подделки отчетности, штрафы от ФНС.<br>**Коммерческая тайна:** Данные о выручке и маржинальности. | **1C:** Ограничение доступа на уровне сетевого экрана (Firewall), VPN для удаленного доступа бухгалтера.<br>**Интеграция:** Взаимная аутентификация (mTLS) при обмене данными между 1С и Backend.<br>**At Rest:** BitLocker на серверах Windows, где работает 1С. |
| **5. Данные для аналитики (Data Lake)**<br>*(Обезличенные выгрузки для отчетов, статистики)* | **Приватность:** Риск нежелательной идентификации при недостаточном обезличивании.<br>**Риск:** Утечка коммерческих тайн конкурентам. | **ETL:** Процедуры анонимизации до сохранения в ClickHouse.<br>**Доступ:** Доступ к ClickHouse только на чтение (Read-only) для аналитиков.<br>**Сетевая защита:** Изоляция аналитического контура сети от основного production-контура. |
| **6. Резервные копии (Backups)**<br>*(Дампы БД, снапшоты дисков)* | **Доступность:** Защита от шифровальщиков (Ransomware).<br>**Конфиденциальность:** Бэкап - это полная копия данных, часто забываемая и слабо защищенная. | **Storage:** Хранение в неизменяемом (Immutable) S3-бакете (защита от удаления).<br>**Шифрование:** Обязательное шифрование бэкапов. <br>**Тестирование:** Регулярное тестирование восстановления в "песочнице". |
