# Задание 4. Оценка узких мест при миграции

В компании планируется миграция устаревшей монолитной системы на современную архитектуру (например, на микросервисную). В процессе перехода необходимо выявить потенциально узкие места, которые могут негативно повлиять на работоспособность нового решения.

## Анализ ситуации

### Текущее состояние (As-Is):
  
- Компания работает на базе файловой системы (Excel, PDF) и «1С» в файловом режиме.
- Вся инфраструктура сосредоточена на одном физическом сервере. 
- Процессы ручные, связность систем обеспечивается людьми (ручной перенос данных) или прямыми OLE-соединениями.

### Целевое состояние (To-Be):
- Распределенная микросервисная архитектура (Java, Kubernetes, PostgreSQL, ClickHouse). 
- Внедрение мобильного приложения и веб-портала. 
- Ожидается кратный рост данных и открытие филиалов.
 
## Ключевые изменения:

- Переход от монолитного хранения (файлы) к реляционным и аналитическим СУБД.
- Переход от локальной сети к доступу через Интернет (API Gateway).
- Автоматизация ввода данных клиентами (риск высокой нагрузки на бэкенд).

## Выявленные узкие места 

[Узкие места представлены в форме диаграммы Исикавы](diagram.png)

На основе построенной диаграммы Исикавы выделены следующие критические зоны:

### Данные (Качество и Миграция) - Самый высокий риск

- Проблема: "Грязные" данные в Excel. Отсутствие уникальных ID пациентов, дубликаты, опечатки в ФИО, разные форматы дат.
- Риск: При импорте в строгую схему PostgreSQL возникнут массовые ошибки, либо создадутся дубликаты пациентов, что недопустимо для медицинской системы.
- Узкое место: Процесс ETL (Extract, Transform, Load). Ручная чистка может занять месяцы.

### Интеграция с Legacy-системой («1С»)

- Проблема: «1С:Бухгалтерия» и «Торговля и склад» работают в файловом режиме.
- Риск: Файловая версия 1С плохо работает с параллельными подключениями. При увеличении нагрузки возможна блокировка таблиц.
- Узкое место: Интерфейс обмена между Java-бэкендом и 1С.

### Инфраструктура и Эксплуатация

- Проблема: Текущий IT-отдел не обладает компетенциями для поддержки Kubernetes, Kafka/RabbitMQ, Vault.
- Риск: Неправильная настройка кластера (Resource Limits, Networking) приведет к падению продакшена при нагрузке. Администратор сети может не справиться с отладкой распределенных транзакций.
- Узкое место: Человеческий фактор и сложность эксплуатации Kubernetes.

### Процессы и Персонал

- Проблема: Сопротивление изменениям со стороны персонала, привыкшего к Excel. 
- Отсутствие формализованных процессов тестирования и отката.
- Риск: Саботаж новой системы (продолжение ведения учета в Excel), ошибки при двойном вводе данных на этапе MVP, невозможность быстро восстановить работу в случае сбоя новой системы.

## Рекомендации по устранению узких мест

| Приоритет | Категория | Мера / Рекомендация |
|--|--|--|
| P0 (Критично) | Данные | Предварительная нормализация Excel: Написать скрипты (Python) для поиска дублей и невалидных данных до начала миграции. Создать промежуточную БД для "очистки". |
| P0 (Критично) | Интеграция | Перевод 1С в клиент-серверный режим: Обязательно мигрировать 1С на Postgres. Файловый режим не выдержит интеграцию с Web-порталом. |
| P1 (Высокий) | Персонал | Наем DevOps инженера: Текущий "администратор сети" не сможет обеспечить SLA для Kubernetes. Нужен профильный специалист или аутсорс. Провести обучение для медперсонала. |
| P1 (Высокий) | Архитектура | Асинхронный обмен: Не делать синхронных вызовов в 1С при действиях пользователя. Использовать очереди (RabbitMQ/Kafka) для буферизации запросов к медленным Legacy-системам. |
| P2 (Средний) | Процессы | Параллельный запуск (Parallel Run): На этапе MVP дублировать ввод данных в старую и новую систему в течение 2-4 недель для сверки корректности. Разработать план отката. |
| P2 (Средний) | Инфраструктура | Load Testing: Провести нагрузочное тестирование API Gateway и БД до открытия доступа мобильному приложению. |
